三、根因：一条「查—算—写」的暗扣通道

核心frontend/src/hooks/usePoints.ts 的 updatePoints()：

  • 先从 profiles 读出 current_points；
  • 本地算出 新值 = 旧值 + 变动量；
  • 再把 新值整体写回 profiles.current_points。

它有三个致命性质：没有加锁、没有下限保护、完全不写 point_transactions。 而且它走的是通用的 PUT /api/tables/profiles/:id 接口——老版本里这个接口 任何已登录用户都能改任意表的任意字段。

调用它的地方，每一个都会造成「扣了分但流水里查不到」：

五、为什么现在「28 分」和流水对不上

你手工把 -4900 改成 0 之后，他又答题赚了 28 分，所以现在是 28。 但他的流水仍然保留着被抹掉之前的历史累计 196，于是：

28 − 196 = −168  ←  这个差额就是被手工归零抹掉的那一段，属于正常现象，不代表还有新的扣分。

六、已经做的修复（工作区待提交）

  • 原子接口新增 POST /api/student/points/adjust，余额判断写进 WHERE current_points >= ?，并发安全、天然不会为负；前端 usePoints 已改为调用它。
  • 写保护PUT /api/tables 对 profiles 收口：学生只能改自己、且不能碰积分与权限字段；教师可改但积分强制钳制 ≥ 0。

  • 原子扣减AI 答疑、喂食、换背景、应用扣费全部改为条件 UPDATE + GREATEST(0, ...)。
  • 皮肤限兑同一皮肤只能兑换一次，重复兑换直接 400 且不影响积分。
  • 数据库兜底新增迁移 077 归零历史负分，并在启动时创建 profiles 的 BEFORE INSERT/UPDATE 触发器，把三个积分字段强制钳制 ≥ 0。
